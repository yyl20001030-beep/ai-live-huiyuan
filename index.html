我的客户｜功能迭代说明
已确认规范
规范版本：v3.7.0 (2026-10) 当前预览：直属下级详情
一、功能目标

升级「我的客户」中的直属下级经营信息查询能力，帮助业务人员快速了解下级的商品浏览、加购和购买情况，为日常业务沟通、商品推荐及经营分析提供参考。

本次重点优化商品行为信息的展示方式，让业务人员能够直观了解客户关注的商品、浏览频率、加购时间及购买情况，同时保留直属下级原有的月度业绩查询能力。

二、本次更新内容
1. 直属下级查询
  • 支持查询直属下级并查看基本信息。
  • 保留原有月度业绩查询逻辑。
  • 支持进入直属下级详情页面。
2. 浏览与加购

浏览和加购记录分开展示，根据当前记录的行为类型呈现对应信息：

  • 仅浏览记录：展示浏览图标、最后浏览时间、本月浏览次数及今日浏览次数。
  • 浏览 + 加购记录：上方展示加购图标和加购时间，下方展示本月浏览次数及今日浏览次数。
  • 加购记录不重复展示浏览时间，也不展示本月加购次数或今日加购次数。
  • 两种模式均展示本月购买状态和历史累计购买件数。
  • 支持商品名称搜索、行为筛选和交互频率排序。
3. 交互频率排序

支持按商品交互频率升序或降序排列，帮助业务人员优先查看互动较多的商品。

  • 交互频率由当前月度周期内的浏览次数与加购次数共同计算，仅用于内部排序，不在商品卡片中展示交互总量。
  • 浏览行为按照 SKU 维度统计，不同 SKU 分别计算浏览次数及相关交互频率。
4. 最近下单
  • 沿用页面上方的月度筛选。
  • 仅统计符合有效订单规则的购买记录。
  • 商品数量按实际购买的商品件数计算，不按订单数量计算。
  • 根据商品实际售后结果，判断相应商品是否计入购买统计。
三、业务操作流程
我的 → 我的客户 → 选择直属下级 → 查看基本信息及月度业绩 → 进入浏览与加购或最近下单 → 搜索商品并查看相关信息。
四、本次迭代范围
  • 本次聚焦直属下级的商品行为查询、购买情况及最近下单信息展示。
  • 本次不新增复杂客户标签、客户分类、客户跟进工作流或团队经营报表。
五、核心业务口径
• 统计颗粒度：浏览统计按照 SKU 维度计算。
• 时间周期：月度统计采用自然月。
• 交互频率权重：由浏览次数与加购次数共同决定，但交互总量不在页面展示。
• 下单范围联动：最近下单使用页面上方的月度筛选。
• 售后口径：有效订单及商品售后统计按照研发细则中的确定规则执行。
一、页面与功能范围

本次研发涉及：

  • 直属下级详情页面（双 Tab 容器）。
  • 浏览与加购行为记录展示。
  • 商品搜索、行为筛选及交互频率排序。
  • 最近下单查询与商品购买件数统计。
研发原则：保留现有直属下级查询、月度业绩查询、页面导航及其他无关功能。本次侧边栏 UI 改造本身不得修改左侧 App 页面及业务逻辑。
二、浏览与加购展示规则
1. 仅浏览记录

展示字段：商品图片、商品名称、浏览图标及行为标识、最后浏览时间（格式为 MM-DD HH:mm）、本月浏览次数、今日浏览次数、本月购买状态、历史累计购买件数。

禁闭规则：仅浏览记录不展示加购图标、加购时间、本月加购次数或今日加购次数。
2. 浏览 + 加购记录

展示字段：商品图片、商品名称、加购图标及行为标识、加购时间（格式为 MM-DD HH:mm）、本月浏览次数、今日浏览次数、本月购买状态、历史累计购买件数。

  • 不展示项：不展示本月加购次数、今日加购次数、浏览图标、浏览标识或最后浏览时间。
  • 加购记录层级：上方展示加购行为，下方保留浏览统计。加购时间必须来自对应加购事件，不得用浏览时间代替。
3. 浏览与加购事件处理
  • 浏览和加购事件分别存储、分别识别。
  • 同一商品存在两种行为时，可以分别形成浏览记录和加购记录。
  • 每条记录只展示自身对应的行为类型。
  • 浏览次数只能由浏览事件计算，不得将加购事件计入浏览次数。
  • 隐藏加购次数不代表删除底层加购事件数据。
  • 不得为了减少重复商品而将浏览和加购强制合并为一条混合记录。
三、统计周期与时间口径
  • 1. 自然月周期：月度统计采用自然月，即所选月份的 1 日至当月最后一日。页面上方现有的月度筛选是统一的月份选择依据。不得新增与之冲突的独立月份筛选。
  • 2. 浏览统计：本月浏览次数统计当前所选自然月内的浏览事件；今日浏览次数统计当前日期内的浏览事件；最后浏览时间取当前所选自然月内最新的浏览事件时间；浏览统计按 SKU 维度计算。
  • 3. 加购时间：加购时间取对应加购事件的实际发生时间，采用 MM-DD HH:mm 格式；不得使用浏览时间代替加购时间；页面可以不展示加购次数，但底层事件必须保留，以支持交互频率排序。
  • 4. 时间边界：自然月统计必须正确处理每月第一天、最后一天、跨月事件及闰年二月等边界情况；今日统计与自然月统计是两个独立口径，不得将今日次数误当成本月次数。
四、商品维度与交互频率排序
  • 1. SKU 维度：浏览行为按照 SKU 维度统计。不同 SKU 分别计算浏览次数、最后浏览时间及对应交互频率，不得直接合并为同一个 SPU 的浏览统计；确保行为数据能通过明确的 SKU 标识与商品记录正确关联。
  • 2. 交互频率计算：
    商品交互频率 = 当前所选自然月浏览次数 + 当前所选自然月加购次数
    交互频率仅用于内部排序，不在页面中展示对应总量、标签或数值。
  • 3. 筛选规则：「全部行为」展示符合条件的浏览记录和加购记录；「仅看浏览」只展示浏览记录；「仅看加购」只展示加购记录。商品搜索与行为筛选支持组合使用。
  • 4. 排序规则：支持升序与降序；无论当前选择全部行为、仅看浏览还是仅看加购，排序均基于相同的商品级交互频率；同一 SKU 的浏览记录和加购记录必须使用一致的商品级交互频率；切换月份后重新计算排序结果。
五、购买状态与历史累计购买件数
  • 1. 本月购买状态：展示「本月已购买」或「本月未购买」。购买状态应根据实际购买数据判断，不能因浏览或加购行为直接认定为已购买。
  • 2. 历史累计购买件数：按实际商品件数计算，不是订单数量。统计必须扣除取消、退款、整单售后以及部分售后中应扣除的商品件数。
六、有效订单与售后统计规则
【已确认业务口径，不得擅自修改】
1. 有效订单定义：指正常流程中未发生取消、退款或整单售后的订单。发生整单取消、退款或整单售后时，该订单中的商品均不计入有效购买统计。
2. 部分售后处理：发生部分售后的订单，必须按照具体商品的售后结果分别判断：
  • 商品未发生售后：继续计入购买统计。
  • 商品售后退款：该商品不计入有效购买统计。
  • 商品售后换货：该商品继续计入购买统计。
* 不得因为订单中某一个商品发生部分售后，就将其他未售后的商品一并排除。
3. 历史购买件数扣减：历史累计购买件数必须扣除：取消订单件数、退款订单件数、整单售后件数、部分售后中退款商品件数。部分售后中未售后商品与换货商品继续计算。
4. 数量口径：商品购买数量必须按照实际购买的商品件数统计，而不是订单数（例如订单包含 SKU A 2件、SKU B 3件，合计为 5 件，不是 1 单）。
七、最近下单页面
  • 时间范围：沿用页面上方现有的月度筛选。
  • 月度周期：自然月。
  • 订单口径：遵循上述已确认的有效订单及商品售后规则。
  • 商品数量：按有效购买的实际商品件数统计。
  • 保留商品搜索、商品图片、商品名称、下单时间及购买件数等现有功能。
  • 月度切换后，订单列表与商品件数统计必须同步更新。
八、数据与接口要求

Mock 数据模型支持项核对：

  • 商品及 SKU 标识区分。
  • 浏览和加购事件类型及绝对时间记录。
  • 对应商品的购买件数及订单状态标识。
  • 商品售后状态（未售后/退款/换货）及统计过滤逻辑。
  • 严格杜绝通过硬编码次数或固定文案伪造统计结果。
九、UI 与交互验收标准
• 侧边栏验收：默认业务说明；Tab 平滑切换；独立滚动条；长内容不被截断；层级清晰无密集文本。
• 模式 A 验收：仅浏览记录只展示浏览图标、时间及次数，无加购信息。
• 模式 B 验收：加购记录上方展示加购图标和时间，下方展示浏览次数，严格不展示加购次数和最后浏览时间。
• 统计验收：浏览按 SKU 统计；月度按自然月；排序按浏览+加购之和但页面不显示交互总量；有效订单件数准确扣除退款。
